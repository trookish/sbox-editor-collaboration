## S1 — transient transforms and undo

**Read.** `SceneAdapter.Capture(Scene)` calls `gameObject.Serialize()`, clones its JSON, removes `Children`, and flattens by `__guid` and parent (`Editor/SceneAdapter.cs:46-79`). `Apply(SceneEditorSession, Dictionary<string,ObjectState>)` takes a full capture and diff, validates, creates/deserializes missing objects, reparents, writes `Name`, `LocalPosition`, `LocalRotation`, `LocalScale`, `Enabled`, and tags directly, deserializes changed component data, destroys removed objects, and marks unsaved (`Editor/SceneAdapter.cs:81-145`). It does **not** itself call `UndoSystem.Initialize()` or open an undo scope. Engine exposes `P:Sandbox.GameObject.LocalTransform` and `P:Sandbox.GameObject.WorldTransform` (`Sandbox.Engine.xml:31729,32351`); the existing direct `LocalPosition` etc. setters are the relevant non-undo-scope example. By contrast, built-in editor MCP edits explicitly use `session.UndoScope(...).WithGameObjectChanges(...).Push()` (`Mcp/Scene.cs:431-440`). No read source proves that arbitrary direct setter writes can never be recorded implicitly.

**Read.** On snapshot, receiver calls `SceneAdapter.Apply` then `UndoSystem.Initialize()`, clears collaboration undo and calls `MirrorNativeUndo` (`Editor/CollaborationSession.cs:2610-2642`). Own merged/rebased receipt does the same (`:2713-2718`), own final receipt calls `Initialize()` even without a rebase (`:2721-2733`), and **every applied other-peer accepted receipt** calls `Apply`, captures LastOrder, `Initialize()`, `MirrorNativeUndo` (`:2737-2769`). The mirror inserts one `"Collaboration Undo"` entry for the latest locally acknowledged operation (`:3124-3147`); `Undo()` uses a separate tracked stack (`:3093-3121`). UI text explicitly says each commit clears native history (`Editor/Dock/CollaborationDock.cs:87`). Engine XML `M:Sandbox.Helpers.UndoSystem.Initialize` says "Clear the history and take an initial snapshot" (`Sandbox.Tools.xml:11187-11191`); `SetSnapshotFunction(System.Func{System.Action})` describes saving/restoring entire project state (`:11146-11151`). `M:Editor.SceneEditorSession.SuppressUndoSounds` only suppresses *sounds* (`Sandbox.Tools.xml:8186-8189`), not recording; `FullUndoSnapshot(System.String)` takes a full scene snapshot (`:8191-8194`). No suppression-of-recording member was found in these documented members; absence of an API in XML is **not** proof none exists.

**Inferred.** Thirty remote accepted transform receipts per second imply up to thirty full `Capture`/`Diff` passes (`SceneAdapter.Apply`) plus thirty undo clears/initial snapshots per second, not merely thirty property sets. Exact frame cost and snapshot allocation are **Unknown**; clearing native Back/Forward history is documented, so earlier unrelated native Ctrl+Z history is lost each time. The local collaboration stack is not cleared for each remote receipt; the mirror is rebuilt from its top. If a sender's drag commits only once, the receiver pays this cost once, not at the presence-frame rate: measure actual accepted receipt cadence, not assume 30 Hz.

**Recommendation — Inferred, conditional.** Keep in-flight remote drag data outside `ObjectState`/accepted packets as a transient presence-like stream; apply `LocalTransform` directly to a separate preview/puppet object (or a quarantined view transform), restore/replace it on accepted authoritative packet, and do not call `SceneAdapter.Apply`/`Initialize` for every preview. Avoid modifying the actual authored object until the accepted packet unless a live probe confirms undo and local edit sampling can distinguish previews. A `Gizmo.Draw` ghost is a viable **Unknown** fallback: `P:Sandbox.Gizmo.Draw` exists (`Sandbox.Engine.xml:5330`), but no read evidence establishes its lifecycle, shape fidelity for arbitrary meshes, or scene-view visibility. Direct transform preview offers real renderer fidelity but must be isolated from `Capture` (`CollaborationSession.cs:2167-2192`) to avoid an echo. For committed receipts, redesign native-undo integration to retain unrelated history only after verifying a narrow undo API; do not simply skip `Initialize()` and risk stale native undo entries. Probes 1–2 below settle this.

## S4 — `ObjectState` coverage

**Read.** `ObjectState(string Id, string Parent, JsonObject Data)` and `Packet.Changes: List<Change>`/`Objects: List<ObjectState>` are whole-object JSON envelopes (`Editor/Core/Protocol.cs:9-11,53-57`). `Capture` serializes scene root game objects, not scene properties (`Editor/SceneAdapter.cs:46-79`); source scan runs every 50 ms and validates every changed object (`Editor/CollaborationSession.cs:2096-2097,2167-2192`). `ObjectFields` is exactly `Name, Position, Rotation, Scale, Enabled, Tags`; `ComponentFields` allows `Sandbox.ModelRenderer.Tint`, six `Sandbox.CameraComponent` scalar fields, three `Sandbox.DirectionalLight`, three `Sandbox.PointLight`, three `Sandbox.BoxCollider` fields (`Editor/Core/Protocol.cs:230-239`). A `Before=null`/`After=null` creation/deletion is allowed only if *every* component type is on that list and its JSON has no nonempty nested object/array except four boolean ModelRenderer `RenderOptions` keys (`:359-385`); an empty component list can pass. For existing objects, non-allowlisted changed object property, component array count, property, or non-scalar value throws (`:387-423`). `Apply` only updates existing components by matching GUID and `DeserializeImmediately`; it does not add/remove/reorder components (`Editor/SceneAdapter.cs:125-134`). The distinction between "captured in JSON" and "admitted, applied, round-tripped" matters.

**Hard-failure sites — Read.** The source-scanner catches exceptions and calls `Fail(ex.Message, ...)` (`Editor/CollaborationSession.cs:2196-2199`). An unsupported local edit reaches the explicit throws at `:2103` (play without approved source coexistence), `:2161` (scene file changed outside collaboration save), `:2165` (scene properties/metadata/navmesh), `:2173` (object disappeared from serializable capture but still exists), and `:2190` (`StateRules.ValidateChange`, which throws the exact unsupported identity/prefab/creation/graph/property/component/scalar reasons at `Editor/Core/Protocol.cs:342-424`). Sibling order throws at `SceneAdapter.ValidateSiblingOrder` (`SceneAdapter.cs:147-160`) invoked at `CollaborationSession.cs:2176`. Remote application has additional failure points: routing refusal `CollaborationSession.cs:2211`, no tracked target `:2600,2604`, and `SceneAdapter.Apply` at `:2635,2715,2765` (validation at `SceneAdapter.cs:88-92`, GUID preservation `:97-100`, missing components `:129-134`). These are not silent skips and cannot satisfy "no errors whatsoever" for the listed edits without expanding validation and apply semantics. Full snapshot subscription initially validates graph, not the entire edit allowlist (`Protocol.cs:475-480`); existing complex content may therefore appear initially but fail on edit.

**Mesh wire-cost estimate — Inferred, with an important limit.** For an accepted changed object `Change` contains both `Before` and `After` full `ObjectState` (`Protocol.cs:9-11,53-57`): if mesh JSON is inline and serializes to **B bytes**, one vertex costs approximately **2B + packet framing**, e.g. a 1 MiB component produces roughly 2 MiB/receipt, or ~60 MiB/s at 30 receipts/s before fanout. This is a hypothetical size, *not* a measured s&box mesh size. The observed engine sample instead stores a small `$blob` GUID in `Mesh.Data` (`pregamelobby...scene:232-238`); reference-only JSON costs O(1) but cannot reproduce changed geometry on another machine unless corresponding blob bytes are captured/transferred. XML `BlobContext.SaveTo(JsonNode)` explicitly stores captured blobs alongside JSON (`Sandbox.Engine.xml:65195-65198`); current `SceneAdapter.Capture` does not call it. A field-level delta within the `Mesh` JSON property alone is insufficient for a binary `MeshBlob`: implement stable vertex/face operations or region/chunk delta plus blob lifecycle, and measure real serialization and payload length in probe 4. Never claim the GUID by itself round-trips an edited mesh.

## S6 — play, puppet, video, game client

**Editor/runtime scene — Read.** `SceneEditorSession.All`, `.Active`, `.GameSession` are documented (`Sandbox.Tools.xml` `P:Editor.SceneEditorSession.All`, `.Active`, `.GameSession`, lines 8059-8068,8161-8164). `SceneEditorSession` holds an open Scene, selection and undo (`T:Editor.SceneEditorSession`, `:8053-8057`). Editor `Mcp/Play.cs:11-33` calls `EditorScene.Play()` and `EditorScene.Stop()`; `Scene/SceneView/ViewportTools.Center.cs:85-95` calls `EditorScene.Play(sceneViewWidget.Session)` and `.Stop()`. `Scene/SceneView/SceneDock.cs:12` resolves `_editorSession.GameSession ?? _editorSession`; `SceneViewWidget.Game.cs:17-25,48-61` switches to a Game view and F8 ejects to `GameEjected`. `Mcp/Scene.cs:12-25,37-64` enumerates `SceneEditorSession.All`, labels `GameEditorSession` separately, then walks `session.Scene.Children`; `Editor/RuntimeSceneAdapter.cs:12-46` identifies runtime `session.Scene`, source `session.Parent.Scene`, captures its root objects recursively, and excludes `NotSaved` objects (`:66-90`). Runtime scene is a distinct game session parented to edit session; whether playing truly produces a copy with stable IDs in every scene is **Unknown** despite `CollaborationSession.cs:2090-2094` commenting so. `SceneEditorSession.IsPlaying` is consumed in editor code (`ViewportTools.Center.cs:19-25`) and collaboration (`CollaborationSession.cs:2101`). No public XML `SetPlaying`/`StopPlaying` signature was found in examined entries; use observed `EditorScene.Play/Stop` call pattern, not an invented method.

**State-stream puppet — Read/Inferred.** `Scene.Load(SceneLoadOptions)` exists (`Sandbox.Engine.xml` `M:Sandbox.Scene.Load(Sandbox.SceneLoadOptions)`, lines 35768-35772); documented `SceneLoadOptions.DeleteEverything` only controls `DontDelete` removal (`:63341-63345`). No documented load flag disabling component execution was found in examined options. `Component.Enabled` exists (`Sandbox.Engine.xml` `P:Sandbox.Component.Enabled`, line 21131). **Inferred:** a safe spectator must either instantiate only allowlisted visual components into a separate non-game editor scene, or explicitly disable/remove every behavior, physics, audio, network, and camera controller component before ticking; deserializing arbitrary game scripts and hoping `IsProxy` prevents effects is unsafe. Even editor sessions can tick (`Sandbox.Tools.xml` `P:Editor.SceneEditorSession.ShouldUpdate` references `Scene.EditorTick`). Runtime creation requires state for new IDs and parent, visual component type/fields, and prefab asset path/override mapping for runtime-spawned prefab instances; `RuntimeSceneAdapter.Capture` serializes objects but current allowlists exclude prefab fields (`Editor/Core/RuntimeProtocol.cs:14-23,44-54`). **Unknown:** whether disabled components can have `OnAwake`/deserialize side effects before disabling and whether a component-free, renderer-only scene can display all user visuals. Free-fly camera in editor has `Application.Editor.Camera` and mutable viewport camera state copied to camera every frame (`Mcp/Scene.cs:164-218`); editor F8 eject already exercises a free camera in a **local** playing viewport (`SceneViewWidget.Game.cs:42-61`). A custom game-view implementation would need `CameraComponent` and input/camera control; there is no evidence it can attach to a remote author's scene directly.

**Video fallback — Read/Inferred.** XML has `M:Sandbox.CameraComponent.RenderToBitmap(Sandbox.Bitmap)` and overload `(Sandbox.Bitmap,System.Boolean)` (`Sandbox.Engine.xml:20130-20135`). `Sandbox.Bitmap.ToJpg(System.Int32)`, `.ToPng`, `.ToWebP(System.Int32)`, `.GetBuffer` exist (`:18192-18226,17938-17945`); editor source actually uses `new Bitmap(width,height); camera.RenderToBitmap(bitmap,false)` on *editor camera* (`Mcp/Scene.cs:221-239`). **Unknown:** rendering a camera from `GameEditorSession` while playing, timing/thread affinity, GPU readback latency, returned encoding/bytes, and transport/UI decoding in remote dock. Raw RGBA 1280×720×4×30 = **110,592,000 bytes/s ≈ 105.5 MiB/s** one viewer; compressed JPG size is scene/quality-dependent and must be measured. This is an order-of-magnitude *raw* estimate, not claimed video throughput.

**Join game as client — Read/Inferred.** XML `M:Sandbox.Networking.CreateLobby(Sandbox.Network.LobbyConfig)`, `.CreateLobby`, `.Connect(System.String)` (`Sandbox.Engine.xml:43846-43876`); `T:Sandbox.NetworkHelper` creates lobby and assigns player prefab on active connection (`:26703-26726`). [Network Helper docs](https://sbox.game/dev/doc/networking/network-helper) say `StartServer` creates lobby when not joining, and `OnActive` creates/owns `PlayerPrefab`; [testing multiplayer docs](https://sbox.game/dev/doc/networking/testing-multiplayer) document new local instance and `connect local`. Editor `Mcp/Network.cs:36-47,82-97` starts hosting from editor and spawns a **separate `sbox.exe` game client**, not necessarily a second editor instance. **Unknown:** whether another running editor can `Networking.Connect` to the player's editor-hosted lobby via Steam ID, IP, direct connection, or `local`, and how to suppress `NetworkHelper` player spawn for a spectator. A normal client may be assigned a player and execute full game logic. **Inferred:** join-as-client cannot be the universal solution: a singleplayer scene may have no lobby, and multiplayer games' own network/player-spawn policy needs opt-in spectator support. A collaboration spectator stream must remain independent of game's network configuration.

**Existing runtime pieces — Read.** `PlaySpectateRules.Decide` pauses source synchronization on unapproved local play, while presence remains; `HeldPacketBuffer` holds only `snapshot`/`accepted`, capacity 4096 (`Editor/Core/PlaySpectate.cs:24-52,84-128`). `CollaborationSession.cs:2090-2094` stops source sampling while playing and `:2035-2052` handles held packet overflow. `RuntimeSceneAdapter.Describe/Capture` binds game session to source and serializes valid saved runtime objects (`Editor/RuntimeSceneAdapter.cs:12-47,66-91`). `PlanApply` and `Apply` both only plan (`:49-64`), and planner always returns `Unsupported` (`Editor/Core/RuntimeSceneAdapterContract.cs:231-249`). `RuntimeProtocol` has run identity/field allowlists (`Editor/Core/RuntimeProtocol.cs:10-23,25-85`), `Protocol.ValidateRuntimeEnvelope` checks run ID and monotonic sequence (`Editor/Core/Protocol.cs:200-223`), and `RuntimeAuthority` has experimental operation admission (`Editor/Core/RuntimeAuthority.cs:344+`). `PlayModeLifecycle` explicitly says "transport, sampling, and runtime apply remain unsupported" (`Editor/Core/PlayModeLifecycle.cs:207-217`). **Inferred:** reuse run/sequence identity, source-vs-runtime isolation, read-only capture, and lifecycle; add frame sampler, compact delta format, broadcast transport and receive/apply into a **separate spectator view**, lifecycle snapshot/recovery, authority/permission, asset/blob transfer, and a non-executing visual whitelist. Do not reinterpret `RuntimeSceneAdapter.Apply` as implemented mutation.

**Build order — Inferred, conditional.** (1) Minimal read-only state-stream mirror for transforms/enable/create/delete with verified visual-only prefab/mesh handling and free camera: independent of game's multiplayer and preserves local scene content. (2) Video fallback for unsupported visuals *after* proving play-camera readback/encoding budgets; video cannot itself provide free-fly, so label that limitation and keep the mirror for navigation if possible. (3) Join-as-client only as opt-in integration for multiplayer projects with spectator spawn policy; do not force a singleplayer game to become networked. If probe 5 cannot produce a non-executing visible puppet safely, move video proof ahead of production mirror, but do not promise remote free-fly from video alone.
