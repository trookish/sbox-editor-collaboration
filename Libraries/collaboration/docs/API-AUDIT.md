## Bounded runtime schema contract (Task 3)

`RuntimeStateRules` is a pure, engine-independent validator for the **initial bounded runtime schema only**. It does not sample a play-mode scene, apply runtime state, or add runtime support to the editor transport. A future adapter must validate a complete snapshot, including its separately supplied `scenes/...` path, before any apply operation.

The allowed GameObject serialization keys are exactly `__guid`, `Name`, `Components`, and the runtime fields `Position`, `Rotation`, `Scale`, `Enabled`, and `Tags`. Unknown or prefab fields are rejected, including metadata such as `NetworkMode`. The scalar runtime GameObject fields (`Position`, `Rotation`, `Scale`, `Enabled`, and `Tags`) and every allowlisted component inspector value must be represented by a `JsonValue` whose JSON kind is `String`, `Number`, `True`, `False`, or `Null`; ordinary `JsonObject`/`JsonArray` nodes and `JsonValue` nodes backed by object/array `JsonElement` values are rejected. `__guid` and `Name` remain non-null JSON strings, and `Components` remains the required JSON array. `ModelRenderer.RenderOptions` is therefore not accepted by this initial runtime contract.

The initial component/property allowlist is:

| Component | Properties |
| --- | --- |
| `Sandbox.ModelRenderer` | `Tint` |
| `Sandbox.CameraComponent` | `FieldOfView`, `Orthographic`, `OrthographicHeight`, `ZNear`, `ZFar`, `BackgroundColor` |
| `Sandbox.DirectionalLight` | `LightColor`, `SkyColor`, `Shadows` |
| `Sandbox.PointLight` | `LightColor`, `Radius`, `Shadows` |
| `Sandbox.BoxCollider` | `Center`, `Scale`, `IsTrigger` |

Snapshot validation also requires well-formed GUID identities. Equivalent valid GUID representations are accepted, but object, component, and parent identities are compared by their canonical `Guid.ToString("D")` value so alternate formats cannot bypass uniqueness or graph checks. Parents must exist and graphs must be acyclic. Scene paths must contain no backslashes, empty or `.`/`..` segments, or control characters, and must be `.scene` files below `scenes/`. **This is not all runtime state.** Serialization metadata beyond the exact keys above and any component/property outside the table fail closed until an explicit schema revision adds them.

## Runtime authority contract (Task 4)

`RuntimeAuthority` is a pure, engine-independent, single-threaded state machine. It accepts only `Packet.Kind == "runtime-operation"` envelopes using `Protocol.CurrentVersion`, `CollaborationMode.RuntimeExperimental`, a nonblank operation ID and peer ID, a nonblank `RuntimeRunId`, a safe `scenes/...scene` path, a positive `RuntimeSequence`, a non-negative `RuntimeTick`, and `RuntimeOperationKind` equal to `snapshot` or `edit`. Source edit packets and other transport/session packets are rejected. It defines no socket, queue, runtime adapter, or play-mode behavior.

Authority namespaces are isolated by the exact pair `(RuntimeRunId, ScenePath)`. A run ID is bound to its first accepted scene, and a different run ID starts a fresh namespace even when it reuses the same peer, operation ID, object GUIDs, tick, sequence, or scene. Receipt identity is `(Peer, Id)` inside that namespace. A duplicate accepted operation returns the original accepted receipt without invoking the journal or mutating state again. Rejected operations are not entered into receipt history, so repeating a rejected operation is reevaluated and rejected again. Reusing an operation ID under a different peer, run, or scene does not return the old receipt.

The first operation for a run must be a complete `snapshot`. Accepted sequence numbers are strictly increasing within each run/scene namespace; zero, negative, duplicate, stale, or late sequence numbers are rejected. Ticks are also non-decreasing, so a packet from an earlier tick is rejected. Rejected envelopes do not advance the last accepted sequence or tick, allowing a later valid operation to use that sequence. The revision increases by exactly one only on an accepted operation.

Snapshot operations validate the complete object set and graph through `RuntimeStateRules`. Edit operations validate every before/after state and the complete candidate graph before journal persistence. Each object is compare-and-swap against current authority state: a stale same-object edit rejects the entire multi-change operation, while independent-object edits merge. The first accepted edit wins. Compare-and-swap identity comparison canonicalizes valid object, serialized `__guid`, parent, and nested component `__guid` representations before comparing immutable state, so equivalent alternate GUID spellings are not stale; malformed or mismatched identities are still rejected. Object, component, parent, scene-path, and graph validation remains separate from unchanged source `StateRules` behavior.

All accepted operations are atomic: the authority constructs and validates a complete next state, captures the validated envelope identity and cursor metadata, creates the deterministic canonical receipt, and invokes the journal callback with a separate deep-cloned receipt before committing state, revision, last sequence/tick, namespace binding, or receipt history. Callback mutation therefore cannot alter the returned or retained receipt, and a re-entrant `Apply` is rejected for the duration of the commit window. The journal callback may mutate or retain its argument, or mutate the caller's original operation packet; even when it does, the authority does not read caller-owned metadata after the callback, so the commit and any failure receipt retain the captured pre-callback identity. A callback that mutates the original packet and then throws still leaves authority state, cursors, and receipt history unchanged. If validation fails, a conflict occurs, malformed payload copying fails, the journal callback throws, or a re-entrant apply occurs, the result is a `reject` receipt with an actionable `Error`; authority state, revision, sequence/tick, and receipt history remain unchanged. A validation rejection does not invoke the journal, while a failed journal callback is invoked once but does not commit authority state, revision, sequence/tick, or receipt history; successful journal persistence is the commit boundary. Rejected receipts are not retained as duplicate receipts; the same rejected envelope is evaluated again and remains rejected. This makes a failed journal operation retryable rather than silently acknowledging it as applied. A journal callback that writes and then throws violates the callback's required all-or-nothing persistence contract; `RuntimeAuthority` cannot undo an external side effect it did not own. Caller-owned payload mutation is not persisted as a retry token; a caller must retry with a fresh, valid packet carrying the same operation identity.

Accepted and rejected result packets use existing `Packet` conventions: `Kind` is `accepted` or `reject`; the receipt carries the operation ID, peer, run ID, scene, sequence, tick, operation kind, and current revision; rejects carry an actionable error. Callers must invoke `Apply`, `State`, and the journal callback synchronously on one editor frame or server pump thread. The class deliberately uses no locks and is not thread-safe.

## Runtime scene adapter boundary (Task 5)

`RuntimeSessionGuard` is validation-only. It accepts a non-null, valid, non-destroyed runtime `Game` session whose parent is the expected source session and whose source path matches. It rejects source, destroyed, wrong-parent, wrong-path, and unsafe-path sessions, and exposes no source Save/Reload/dirty/undo/apply mutation surface.

`RuntimeSceneAdapter` capture reads only the runtime `GameEditorSession.Scene`; the `SceneEditorSession` argument is used solely to verify the expected source identity and path, never to read or mutate the source scene. Capture uses `scene.Push()` and copied child lists, excludes the root and `NotSaved` bookkeeping objects, normalizes typed JSON through `ToJsonString()` and `JsonNode.Parse()`, and projects only the Task 3 allowlist. Null root/child entries fail visibly, and the runtime `GameObject.Id` must canonically match serialized `__guid` before capture is accepted. Destroyed or invalid runtime objects fail visibly.

`PlanApply` validates the complete current and target snapshots and graphs before producing deterministic target-only operations. `Apply` is currently a fail-stop alias that returns an `Unsupported` plan; runtime mutation, runtime undo, source dirty flags, persistence, and disk writes are not implemented.

This does not add runtime transport, runtime sampling, or runtime apply. Task 6 adds an explicit opt-in lifecycle around the runtime session: rejected start/stop events preserve pending identity, an approved matching active run lets the existing authoring-source sampler continue, and default-off, wrong-parent, and nonmatching play states remain visible failures. Hotload blocks the lifecycle and recovery reset is rejected until a successful archive is recorded. Pending connects are detached before frame promotion and disposed on completion. A teardown or archive failure is terminal for the current editor session: it remains visible, cannot be cleared by a second begin, reset, or no-connection completion, and never enables or reports hotload recovery. Leave may enable deferred recovery only after the hotload archive succeeded and a detached pending teardown has completed; ordinary Leave never invokes hotload recovery. Source packets are admitted before connection promotion and draining, and each scene-bearing snapshot/accepted packet is routed through one shared canonical-key seam that normalizes case and separators on both the packet key and the tracked target, and fails closed (visibly, with a bounded diagnostic) instead of silently skipping a missing or invalid key or a missing current target.

Task 6 also makes `Start` and `Reconnect` transactional: a pure non-mutating `ValidateStart`/`ValidateReconnect` runs every guard first, and only an accepted validation reaches `BeginStart`/`BeginReconnect`, which run the potentially-throwing preparation and then commit. A rejected or failed preparation therefore never clears prior leave authorization, deferred hotload recovery, or teardown state, and a throwing preparation becomes a typed reject with a bounded diagnostic rather than an escaping exception. Reconnect additionally requires an explicit `CollaborationTransportState` of `Failed` or `Disconnected` for an attached transport, so a live or merely connecting/ambiguous transport is still refused, and an unobserved completed teardown blocks both `Start` and `Reconnect` and is reused rather than overwritten by a `CompleteWithoutConnection` replacement. Disposal of the transport and host server goes through `ResourceDisposalRules.DisposePair`, which always attempts both resources and combines bounded diagnostics, and transport/server/peer diagnostics are bounded at every storage boundary through `CollaborationTransportDiagnostics`. The connected two-editor play-mode source-convergence check is compile-safe and present, but remains unexecuted until `Prepare-EditorTests.ps1` successfully creates and starts both disposable editors.

## Security posture and known gaps

Read this section as the authoritative statement of what the identity machinery does and does not guarantee. The short version: the admission rules are **fail-closed**, they are strict, and the check that would make a SteamID trustworthy is now **wired** — a host posts the peer's identity token to the documented endpoint through `Sandbox.Http` and defers admission until the answer arrives — but that HTTP exchange has never been observed executing against the live service, so nothing about a peer's claimed identity has actually been proven on the wire today.

### Known gaps

These are open and current. Items 1–2 are **wired and unit-tested against an
injected fake transport**, but the real network path and the live editor remain
unexercised; items 3 onward are not covered by any test at all.

1. **The verification call is wired, but has never been observed executing against the real service.** `SandboxHttpTokenTransport` posts to the documented endpoint through `Sandbox.Http`, the engine's own HTTP client, with a 10-second deadline, and `SteamTokenHttpVerifier` requires HTTP 200 **and** `Status == "ok"` **and** `response.SteamId == claimedSteamId` — status-only validation is refused. Admission is *deferred*: a hello is neither admitted nor refused on the first pump, and the task is polled from the editor's frame, never blocked on and never given a thread. **Every test in the suite runs against an injected fake transport, and no run has recorded a real request or a real verdict**, so the request/response contract is verified against the documentation and reflection, not against the live service. If the service is unreachable the verdict is `ServiceUnavailable`, which `AllowUnverifiedPeers` may excuse — but the dock exposes "Allow peers whose Steam identity could not be verified" and it is **off by default**, so a default host refuses a peer it could not verify. Turning it on is a deliberate host decision that admits a self-asserted SteamID.
2. **The identity token is obtained and presented to the host for checking; its fetch is now observed, its use is not.** `LocalSteamIdentity` exposes `ServiceName`, and the connect card requests a token via `Sandbox.Services.Auth.GetToken`, polling the returned `Task` in the dock's frame tick (no worker thread is created, because s&box's hotloader suspends managed threads). Every start consumes the cached token and requests a fresh one for the next, because the service refuses a replayed credential, and the host's `This peer's Steam identity token was rejected.` refusal arms exactly one automatic re-request. **The token request has been observed completing in the open editor**: `status` reports `TokenState = obtained`, `TokenLength = 36`, `TokenError = null`, which retires the earlier "never even issued" wording of this gap. What remains unobserved is what the host's verifier does with that token.
3. **No completed Host/Join has been observed.** The live editor's probe state carries `StartState = "started with the signed-in account 76561198964875726; identity token presented (36 characters)"` — a `Start` that returned without throwing — but every reading taken during this documentation pass reports `Status = Offline`, `Connected = false`, `Roster = []`, `Error = null`, and the probe state does not record what became of that start. The practical claim that Host/Join works is therefore **still unproven**. The historical 46-check two-editor suite recorded in [VALIDATION.md](VALIDATION.md) predates protocol 4, transport encryption and the invite-code flow, and would no longer pass as written.
4. **The signed-in account read is proven; `LocalSteamIdentity`'s failure path is not.** The test-only probe's `identity` command read the signed-in account live in the open editor (`SteamId = 76561198964875726`, persona `live spontaneously`, `IdentityReadError = null` — recorded in [`.hermes/tasks/phase0-results.md`](../../../.hermes/tasks/phase0-results.md)), and the `StartState` in item 3 can only be written after `LocalSteamIdentity.TryGet` returned `true`. What remains unobserved is the signed-out path: no editor on this machine is signed out of Steam, so `TryGet` returning `false` with its failure message, and a readiness checklist showing the blocked "Steam sign-in required" row, have never been seen.
5. **`-joinlocal` produces a deterministic *fake* SteamID.** The s&box engine sets `Application.IsJoinLocal` from `-joinlocal` and assigns `Application.LocalInstanceId` from `+instanceid`, documented in the engine as a basis for "a deterministic fake SteamId". This library contains no `-joinlocal` handling of its own, so two local editor instances launched that way can present the same identity and the second will be refused as a duplicate. Local-instance testing needs distinct real accounts or a distinct identity per instance.
6. **The connection preamble is still unprotected; replay is not.** Transport encryption now exists — an invite-derived 32-byte AES-256-GCM session key with a per-connection HKDF key over a `TCS1` + 16-byte salt preamble (see the table above) — so the session key, the claimed SteamID and every scene edit are no longer readable on the wire by anyone who can reach the port. Replay, reordering and dropped frames are now **refused** (the receiver requires the exact next counter; a relay in the path can end a session but not alter it). Two things remain open: the 20-byte preamble itself travels in the clear, and LAN discovery replies carry the session secret in the clear on UDP 27846, which assumes a trusted LAN. Encryption also exists only when **both** peers run this library — an older peer is refused at the preamble rather than downgraded.
7. **Connection-slot exhaustion by a non-handshaking peer — mitigated, not eliminated.** A peer that sends a `hello` the host refuses (wrong key, wrong project, bad identity) now has its socket closed on the same path as every other refusal, so it no longer occupies a 16-slot budget indefinitely. The cap itself is still a global count, so a burst of simultaneous connection attempts from an untrusted network can still be turned into a denial of service; the honest mitigation is a connection rate limit, which is not implemented.
8. **The historical editor evidence predates this overhaul.** See [VALIDATION.md](VALIDATION.md) — the 13 open-editor checks cover the play-mode lifecycle and a real scene/transform edit, not identity, connection, encryption, admission or the current dock, and no live editor has been *observed* hosting or joining a session.
9. **No two-machine test of any kind.** LAN discovery (UDP 27846), UPnP port mapping and the STUN public-endpoint report have never run against a second machine or a real router. Every connection exercised so far is loopback on one machine.
10. **Multi-peer visuals and the dock's interactive controls are unverified.** Nameplates, camera frustums, selection and focus indicators have not been seen with a second editor, and no test has clicked the dock's buttons, checkboxes or collapsible sections — only probe commands have been driven against it.
11. **The two-editor harness has not been re-run since protocol v4, and the probe it installs is stale.** `Tools/EditorProbe.cs` (17.7 KB, 2026-09-28 05:59) is older than the project's `Editor/EditorProbe.cs` (36.8 KB, 2026-09-28 14:20), and `Prepare-EditorTests.ps1` copies the older one into both fixtures. The harness also needs two Steam accounts, or `RequireSteamFriend`/`RequireOrgMember` temporarily set to `false`, because both fixture editors sign into one account. See [Testing collaboration locally](../README.md#testing-collaboration-locally).
12. **Three dock strings still claim the transport is unencrypted or quote stale README text.** `CollaborationDock.FooterTransportLine` (`Editor/Dock/CollaborationDock.cs:24`) and the tooltip on *Allow peers whose Steam identity could not be verified* (`Editor/Dock/ConnectCard.cs:152`) both predate transport encryption and are now wrong, and `CollaborationDock.LimitsParagraph` (`Editor/Dock/CollaborationDock.cs:35-36`) still presents itself as a verbatim quote of the README's *Install and join* / *Explicit limits* wording, which this pass has since changed. All three live in library code, which this documentation pass is not allowed to edit, so they are recorded here rather than fixed. **Resolved by the final cleanup pass:** the footer now states both paths (invite-code and discovery sessions encrypted, Advanced sessions opened with a typed key not), the allow-unverified tooltip states that encryption follows the join path rather than the setting, and the limits note is presented as drawn from the README with a pointer to *Explicit limits* instead of a verbatim quotation.
13. **The mirrored `Collaboration Undo` row exists; nobody has pressed Ctrl+Z on it.** What the live editor shows is `NativeUndoBack = 1`, `NativeUndoTop = "Collaboration Undo"` immediately after a commit, and `NativeUndoBack = 0` once the stack empties — the row the Undo dock lists is really there. What has **not** been observed is the editor's own key dispatch invoking it: a chord needs a key press no probe can send, and the probe has no command that calls `UndoSystem.Undo()`. The body the entry runs *is* exercised — the dock's Undo button and the `collab.undo` shortcut both call the same `Undo()` — but the engine's pop-from-`Back`-then-invoke step, and the `Forward` stack that follows it, are review-only evidence. `IUndoSystemProvider` was deliberately not implemented, so this library does not participate in how Ctrl+Z finds a system.
14. **The three `collab.*` shortcuts were invoked, not typed.** `-Command shortcuts` calls `SaveShortcut`/`UndoShortcut`/`RecoverShortcut` on the same dock instance the dispatcher would use, and all three ran with `ShortcutError = null` while their refusals arrived as recorded session failures (`No acknowledged local operation available to undo`, `No session to recover - start or join one.`) rather than as an exception. What is unverified is the registration half: that the editor's keybind system actually owns `CTRL+ALT+S`/`Z`/`R` under *Collab*, that `ShortcutType.Window` gates them the way the source says it does, and that no other widget already claims those chords.
15. **Toasts are registered, never seen.** `-Command toast` constructs the three real messages and reports `ToastState = "constructed"`, `ToastError = null`, `ToastCount = 3`, `ToastTitles = ["Connection lost", "Connection restored", "Automatic recovery stopped"]` from `ToastManager.All` — the manager really holds them, so they are on their way to being drawn. Nobody has looked at the screen: their placement, the 15-second/6-second retire timers, and whether `DrawTimer = false` reads as intended are all unobserved. The transient prompt and the abort toast were likewise only read back from `ToastManager.All`, not seen.
16. **The silent retry's budget was proven live only after it was found broken.** The first live run — a join to a dead port with `AutoRecover` armed — retried indefinitely and raised *Automatic recovery stopped* more than once, because `Fail` handed the budget back after every decline; the cap that the unit tests hold was therefore not enforced in the running editor. The reset has since been removed from `Fail` (an outage now ends only at connecting, `Leave`, `Start`, or the user re-arming the toggle) and the backoff index corrected, but the re-run that proves three attempts and one toast is recorded in [VALIDATION.md](VALIDATION.md). What remains unobserved everywhere: recovery of a **two-editor** session, a recovery that succeeds against a host that came back, and a recovery with unsaved local changes present.
17. **`dock-layout` ends the pass at `state=faulty; compressed=connect`.** The diagnostic means `ConnectCard`'s own `WantedSize()` is larger than the height the column last gave it; `overlaps=0` and the column as a whole fits. It read `state=ok; compressed=none` at the same build's `dock=278x970`, and changed after the dock was widened to 509 px by the probe's own `OpenDock` calls and after a hot-load. Closing and reopening, redocking to three areas, opening the Performance dock, and a fresh `Build()` did not clear it, and neither did the two invalidations added while diagnosing (`DockTheme.SetText` now calls `UpdateGeometry()` on a real text change; `CollaborationDock.Reflow` now invalidates each card). Those two changes are left in because they are correct on their own terms, but **they are unproven as a fix and the green reading was never reproduced** — see [VALIDATION.md](VALIDATION.md) for the full sequence. **Resolved in the follow-up pass (2026-09-29):** the reading was a false positive — `WantedSize()` is `SizeHint()`, frozen at the width the text was last written at, so any width change flipped it while the actual layout was healthy. The diagnostic now tests `MinimumSizeHint()` plus content overflow, reads `state=ok` at 278/400/509/700 px and after rebuild, and a deliberately force-squeezed card is still reported as `state=faulty` — real compression remains detectable.

## Runtime discoveries

- Engine JSON may contain `JsonValue<Guid>` rather than a string node. Direct `GetValue<string>()` failed in the real editor despite compiling. Capture now normalizes through JSON serialization/parsing before wire comparison.
- Two concurrently starting editor processes contended over the engine's shared `config/addons.json`. Sequential startup succeeded and is used by the test harness.
- Independently importing a copied secondary scene generated different `.meta` GUIDs. The baseline check rejected that mismatch as intended. Fixtures now copy the same metadata.
- ModelRenderer has a nested `RenderOptions` object even with an otherwise simple model. Its four boolean flags are explicitly allowed for creation/deletion; arbitrary embedded structures remain excluded.
- Static editor frame forwarding was needed for reliable service pumping through the development hotload cycle. Gizmo event registration is retained on the singleton service and was exercised in both editors.

## Phase 0 probes (live editor)

The probe's `identity` command additionally read the signed-in account live in that editor — `IdentitySteamId = 76561198964875726`, `IdentityPersona = "live spontaneously"`, `IdentityReadError = null` — which is the runtime read Known gap 4 previously recorded as confirmed only by compilation and reflection. That run left the identity-token request unissued (`TokenState = not-started`); a later run in the same editor has since reported `TokenState = obtained` with a 36-character token, as recorded in Known gap 2.

- **Organization membership works.** `Sandbox.Services.Organization.Get("cyn")` completed on the frame tick (`OrgState=done`, no exception) and returned `Title = "Daloo Works"`, `MemberCount = 1`, and one `Sandbox.Services.Players.Profile` with `Id.ValueUnsigned = 76561198964875726`, `Name = "live spontaneously"`, `Online = true`, `IsFriend = false`, `Avatar = "avatar:76561198964875726"`, `Private = false`. The declared count and the returned array agree, and nothing about this org is hidden — the `OrgMemberAllowlist` fallback remains necessary only for orgs that answer with zero visible members, a case this run does not exercise.
- **Friend/online status works, for every case that was reachable.** `Sandbox.Utility.Steam.IsFriend` and `IsOnline` take a `Sandbox.SteamId` (implicit from `UInt64`) and `Sandbox.Friend` has a `Friend(UInt64)` constructor; all three calls returned without error for the signed-in account (`IsFriend=false`, `IsOnline=true`, `Name` and `IsOnline`/`IsAway`/`IsBusy`/`IsPlayingThisGame` populated) and for a non-member public SteamID (`IsFriend=false`, `IsOnline=false`, `Friend.Name = "[unknown]"`). The user's dock was not touched and no widget was added to a visible window.

What remains unproven after Phase 0 is the two-account case: org membership contains no second account, so friend/online status between two real accounts, and any friend-gated UI behaviour, have not been observed.
